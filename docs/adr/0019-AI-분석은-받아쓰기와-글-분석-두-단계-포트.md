# 0019. AI 분석은 받아쓰기와 글 분석 두 단계 포트로 나누고 모델 목록은 앱이 들고 있는다

- 상태: 채택
- 날짜: 2026-10-09

## 배경

첫 버전은 Gemini 하나로 답변 녹음을 분석한다. 나중에 다른 제공사(Claude, OpenAI)를 붙일 수 있어야 하는데 그중에는 음성을 입력으로 받지 않는 모델이 있다. 사용자는 설정에서 분석 모델을 고르고 싶어 하고, 모델이 바뀌면 같은 답변이라도 채점 경향이 달라진다.

## 후보

1. Gemini 호출을 엔진에서 바로 쓰고 모델 이름은 한 버전으로 고정한다
2. "녹음을 넣으면 피드백이 나오는" 포트 하나를 두고 제공사마다 구현한다
3. 받아쓰기(전문과 단어 시각)와 글 분석(교정, 표현, 체크리스트, 등급) 두 단계로 나눈 포트를 두고, 음성을 직접 듣는 모델은 한 번 호출로 두 단계를 끝낸다

## 결정

3을 고른다.

- `engine/answer` 의 포트: `Transcriber`, `TranscriptAnalyzer`, `AudioAnswerAnalyzer`(한 번 호출), `ModelCatalog`. 제공사 이름이 엔진 코드에 없다
- `engine/answer` 의 경로 고르기: 고른 모델이 음성을 직접 들으면 한 번 호출, 아니면 받아쓰기 후 글 분석. 두 단계 경로는 발음을 "평가 안 함"으로 두고 멈춤과 속도는 단어 시각으로 앱이 계산한다
- 제공사 어댑터는 엔진 층의 제공사 모듈(`engine/ai-gemini`)에, HTTP 클라이언트는 `libs/llm-gemini` 에 둔다. 라이브러리는 포트를 모른다
- 모델 목록은 앱이 들고 있는 검증된 목록이다. 항목마다 모델 id, 표시 이름, 음성 직접 분석 여부, 안정 또는 미리보기. 기본은 안정 모델이고 고른 모델이 사라지면 기본으로 돌리고 알린다
- 답변 결과마다 제공사, 모델 id, promptVersion 을 저장한다
- 키는 제공사 이름으로 구분해 따로 저장한다

## 이유

음성을 받지 않는 제공사는 받아쓰기와 글 분석을 나누지 않으면 붙일 수 없다. 단계를 나눠 두면 새 제공사는 어댑터 모듈 하나만 더하고 경로 고르기와 화면은 그대로 둔다. 후보 2는 음성을 못 듣는 제공사마다 받아쓰기를 따로 구현하게 된다.

제공사의 모델 목록 응답에는 오디오 입력을 받는지 알려 주는 값이 없고, 출력 검사(교정 구절이 전문에 있는지, 값 범위)를 통과하는지는 모델마다 품질 확인 도구로 돌려 봐야 안다. 그래서 목록을 그대로 보여 주지 않고 확인한 모델만 앱에 둔다. 기록 화면의 등급 변화가 모델 교체 때문인지 실력 때문인지 가리려면 답변마다 어느 모델이 분석했는지 남아야 한다.

## 결과

첫 버전에서 두 단계 경로는 테스트 안의 "음성을 못 듣는 가짜 제공사"로만 끝까지 돌린다. Claude, OpenAI 실제 연결과 기기 음성 인식 받아쓰기는 다음 버전에서 정한다. 모델 목록은 앱 업데이트로만 바뀌므로 제공사가 모델을 내리면 다음 업데이트까지 기본 모델로 돌린 상태가 유지된다.
