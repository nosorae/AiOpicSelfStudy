# 설계

모의시험과 한 문항 연습, 두 사이클로 만든다. 둘 다 사용자가 앱에서 직접 시작한다. 두 사이클 모두 "답변 하나"를 남기고, 리포트와 다음 출제는 쌓인 답변 전체를 본다. 요구사항 번호는 `product.md` 를 가리킨다.

## 1. 범위

첫 버전에 넣는 것은 다섯이다.

1. 모의시험: 실제 시험 순서 그대로, 15문항, 이어 보기
2. 한 문항 연습: 앱에서 언제든 질문 하나를 푼다
3. 리포트: 답변별 피드백이 쌓이고, 모의시험은 회차 등급이 붙는다
4. 기록: 회차별 예상 등급 변화
5. 약점 출제: 점수가 낮은 문항 유형을 다음 모의시험과 한 문항 연습에 더 낸다

넣지 않는 것은 서버, 계정, 3문항짜리 짧은 회차다.

## 2. 처음 설정

1. AI 제공사를 고르고 API 키를 넣는다. 첫 버전은 Gemini 하나만 보인다. 서버 없이 사용자가 자기 키를 쓴다. 키는 제공사 이름으로 구분해 Android Keystore, iOS Keychain 으로 보호한다(F1.1, F1.2). 화면 위쪽 안내 카드가 서버 없이 내 키로 보내는 이유와 요금이 잡히는 곳을 알리고, 키 받는 순서 세 단계와 시스템 브라우저로 키 발급 페이지를 여는 "키 받기" 버튼을 둔다. 발급 주소는 제공사 정보(`KeyProvider.keyPageUrl`)에 있어 제공사를 더하면 주소도 함께 더한다. 입력란은 키를 가리지 않는다. 40자 넘는 키를 붙여 넣은 뒤 다 들어갔는지 눈으로 확인하게 하려는 것이다. 붙여 넣으며 딸려 온 공백, 역슬래시, 눈에 안 보이는 문자는 저장 전에 뺀다
2. 녹음한 음성이 Google Gemini 로 간다는 안내에 동의한다. 무료 키로 보낸 음성은 Google 이 제품 개선에 쓰고 사람이 들을 수 있다. 두 플랫폼 모두 마이크 권한 요청보다 먼저 묻는다(F1.3)

앱을 켜면 시스템 스플래시를 잡아 둔 채 저장된 키와 동의 상태만 읽어 갈 곳을 정한다(F1.0). 서베이는 설정이 아니라 모의시험마다 한다.

## 3. 모의시험

| 순서 | 화면 | 실제 시험과 같은 점 | 앱에서 다르게 둔 점 |
|---|---|---|---|
| 1 | 서베이 | 매번 한다. Part 4 에서 12개 이상 고른다 | 지난 선택을 미리 채운다. 매번 12개를 새로 고르는 건 연습에 도움이 안 된다 |
| 2 | 수준 선택 | 1~6단계, Next 뒤 되돌릴 수 없다 | 단계별 샘플 음성은 없다 |
| 3 | 점검과 연습 | 마이크 확인, 채점 안 하는 연습 문항 1개 | |
| 4 | 1~7번 | 아래 문항 규칙 | 40분 타이머가 여기서 시작한다 |
| 5 | 난이도 재조정 | "쉬운/비슷한/어려운 질문" 셋 중 하나 | |
| 6 | 8~15번 | 아래 문항 규칙 | |
| 7 | 끝 | | 리포트가 바로 나온다 |

문항 규칙은 실제 시험과 같다. 질문 글자는 화면에 없다. Play 를 누르면 질문이 나오고 끝나면 녹음이 저절로 시작된다. 녹음 시작 5초 안에 다시 듣기를 한 번 할 수 있다. Next 는 녹음 시작 10초 뒤에 켜진다. 지나간 문항으로 돌아갈 수 없다.

실제 동작을 확인하지 못한 세 곳은 이렇게 정했다.

- 문항별 답변 타이머: 기본은 끄고 설정에서 켠다
- 40분이 지나면: 그때까지 답한 문항만 채점하고 남은 문항은 리포트에 "시간 부족"으로 표시한다
- 앱이 꺼져 있는 동안: 40분 타이머가 멈춘다

## 4. 이어 보기

모의시험 진행은 공통 코드의 함수 하나가 계산한다. 지금 상태와 일어난 일(Play, Next, 다시 듣기, 재조정 선택, 앱 꺼짐, 시간 끝)을 받아 다음 상태를 돌려주고, 저장이나 화면 같은 다른 일은 하지 않는다. 상태가 바뀔 때마다 통째로 Room 에 저장하고, 앱을 켜면 저장된 상태에서 다시 시작한다. Room 에 저장된 상태가 진실 공급원이다.

이렇게 하면 "7번에서 껐다 켜면 재조정 화면부터" 같은 경우를 기기 없이 단위 테스트로 전부 확인할 수 있다. 일어난 일을 모두 기록하고 켤 때 다시 계산하는 방식은 시험 한 회짜리 앱에 비해 크다. 화면이 상태를 들고 있다가 저장하는 방식은 앱이 갑자기 죽으면 저장 시점을 놓친다.

녹음은 몇 초 단위 조각 파일로 바로바로 쓴다. 답하는 도중 앱이 꺼지면 쓰던 조각 하나만 잃는다. 조각을 나눌 때 녹음기를 멈췄다 다시 열지 않는다. 그 사이마다 약 0.07초가 빠져 말 한가운데 음절이 잘린다(11절). 녹음기는 답변 하나 동안 그대로 두고 받은 소리를 쓰는 파일만 바꾼다. 분석 요청에는 조각을 기기에서 한 파일로 이어 붙여 보낸다. 다시 켜면 같은 문항에서 이어 녹음하고, 그 문항에서 다시 듣기를 안 썼으면 질문을 한 번 다시 들을 수 있다. 끊긴 지점은 분석 요청에 표시해서 그 구간을 말 멈춤으로 세지 않게 한다.

## 5. 한 문항 연습

1. 앱에서 언제든 "한 문항 풀기"를 누른다
2. 질문 하나가 나오고 모의시험과 같은 규칙으로 답한다
3. 끝나면 그 답변의 피드백을 바로 보여 준다

## 6. 데이터

기본 단위는 답변 하나다.

- **답변**: 질문, 문항 유형, 주제, 어느 사이클에서 나왔는지, 녹음 조각 목록, 전문, 피드백, 유형별 점수, 분석한 제공사와 모델 id 와 promptVersion
- **모의시험 회차**: 서베이 선택, 수준 선택, 재조정 선택, 답변 순서, 남은 시간, 진행 상태, 회차 등급

녹음 파일은 기기에만 둔다.

## 7. AI 분석

피드백은 답변마다, 등급은 모의시험 전체로 나눠 받는다. 실제 오픽은 문항별 점수 없이 시험 전체를 듣고 등급 하나를 준다. AL 은 모든 문항에서 무너지지 않아야 받는 등급이라 답변 점수 평균으로는 못 잡는다.

- **답변 분석**: Next 를 누르면 뒤에서 바로 보낸다. 한 문항 연습 답변도 같은 경로다. 결과는 전문, 문법 교정, 한 등급 위 표현, 시제 유지, 문단 길이, 말 속도, 멈춘 시간, 롤플레이에서 한 질문 수
- **회차 등급**: 15번이 끝나면 답변 피드백과 녹음을 묶어 한 번 보낸다. 결과는 NL 에서 AL 까지의 예상 등급 범위와, 어느 문항에서 무너졌는지
- **출력 검사**: 교정의 원문 구절이 전문에 있는지, 값 범위와 문항 수가 맞는지 앱 코드가 확인한다(F5.4)
- **실패 처리**: 분석이 실패하면 그 답변만 다시 보낸다. 오프라인이면 녹음은 그대로 하고 분석은 대기열에 넣었다가 연결되면 보낸다. 키가 없거나 틀리면 설정 화면으로 보낸다

### 7.1 두 단계로 나눈 분석 구조

첫 버전 제공사는 Gemini 하나다. 다른 제공사(Claude, OpenAI)를 나중에 붙일 수 있게 분석을 두 단계로 나눈 포트를 `engine/answer` 에 둔다(ADR 0019).

| 단계 | 하는 일 | 결과 |
|---|---|---|
| 받아쓰기 | 녹음에서 전문과 단어마다 시작, 끝 시각을 뽑는다 | 전문, 단어 시각 |
| 글 분석 | 전문(필요하면 단어 시각을 글로)을 받아 교정, 한 등급 위 표현, 체크리스트, 등급을 낸다 | 피드백, 체크 결과 |

경로는 둘이다.

- **한 번 호출 경로**: 음성을 직접 듣는 모델(Gemini 일반 모델)이 녹음을 받아 두 단계를 한 요청에서 끝낸다. 발음까지 본다. 첫 버전은 이 경로만 실제로 쓴다
- **두 단계 경로**: 음성을 못 듣는 제공사를 쓸 때다. 기기 음성 인식이나 받아쓰기 전용 모델로 받아쓴 뒤 글만 보낸다. 발음 항목은 "평가 안 함"으로 표시한다

멈춘 시간과 말 속도는 단어 시각만 있으면 앱이 직접 계산할 수 있다. 두 단계 경로에서는 이 계산을 앱이 맡는다. 한 번 호출 경로의 멈춤, 속도는 모델 답에 맡긴다. 미리 확인 노드 `s1` 에서 모델이 직접 답한 멈춤 위치가 실제와 0.4초 안이었고, 단어 시각까지 받으면 출력 토큰이 분석 한 번보다 많아졌다(11절).

첫 버전에서 두 단계 경로가 실제로 맞물리는지는 테스트 안의 "음성을 못 듣는 가짜 제공사"로 받아쓰기부터 결과 저장까지 끝까지 돌려 확인한다. Claude, OpenAI 실제 구현은 하지 않는다.

### 7.2 모델 고르기와 기록

설정에서 분석 모델을 고른다. 목록은 앱이 들고 있는 검증된 목록이다. 항목마다 제공사(`gemini`), 모델 id, 표시 이름, 음성 직접 분석 여부, 안정 또는 미리보기를 둔다.

목록 API 를 그대로 쓰지 않는 이유는 둘이다. 제공사의 모델 목록 응답에는 오디오 입력을 받는지 알려 주는 값이 없다. 그리고 출력 검사(교정 구절이 전문에 있는지, 값 범위)가 통과하는지는 모델마다 품질 확인 도구(`tools/eval`)로 돌려 봐야 안다. 목록 API 는 고른 모델이 아직 있는지 확인하는 데만 쓴다.

기본값은 안정 모델이다. 미리보기 모델은 2주 공지로 내려갈 수 있어서 고를 때 안내한다. 고른 모델이 내려가 요청이 실패하면 기본 모델로 돌리고 알린다.

답변 결과마다 제공사, 모델 id, promptVersion 을 저장한다. 리포트와 기록 화면에 어느 모델이 분석했는지 보이고, 한 회차 안에서 답변 분석 모델이 섞였으면 회차 등급 옆에 표시한다. 모델마다 채점 경향이 달라서 기록 화면의 등급 변화가 모델 교체 때문인지 실력 때문인지 가려 볼 수 있어야 한다.

무료 키로 보낸 음성이 제품 개선에 쓰일 수 있다는 안내는 음성 전송 동의 화면에 두고 키 입력, 모델 선택 화면에서는 그리로 연결한다.

## 8. 출제

질문은 AI 가 기출 유형대로 만든다. 서베이 주제, 수준, 재조정 선택, 약점 점수를 넣고 문항 유형 순서(자기소개, 3문항 세트 셋, 롤플레이 셋, 비교와 사회 이슈 둘)를 맞춰 받는다.

기출 원문은 앱에 넣지 않는다. 공개된 교재와 기출 모음은 무단 전재 금지이거나 라이선스가 없다. 대신 사용자가 자기 문항 파일을 불러올 수 있게 한다.

질문 음성은 기기 음성 합성으로 읽는다. 비용이 없고 오프라인에서도 된다. 실제 시험 음성과 너무 달라 연습이 안 되면 Gemini 음성으로 미리 만들어 두는 쪽으로 바꾼다.

| 엔진 | `engine/answer` 의 `route/` | 고른 모델이 음성을 직접 들으면 한 번 호출, 아니면 받아쓰기 후 글 분석으로 보낸다. 결과에 제공사, 모델 id, promptVersion 을 붙인다 |
| 엔진 | `engine/ai-gemini` | 어댑터. `engine/answer` 포트를 구현하고 `libs/llm-gemini` 를 부른다. Gemini 모델 목록 항목도 여기 둔다 |
| 라이브러리 | `libs/llm-gemini` | 순수 Gemini HTTP 클라이언트. 포트를 모른다 |
| 라이브러리 | `libs/keyvault` | 키를 제공사 이름으로 구분해 저장한다 |
| 앱 | `apps/opic` | Metro 그래프에서 포트에 어댑터를 묶는다 |

나중에 Claude 를 붙이면 `libs/llm-claude`(클라이언트)와 `engine/ai-claude`(글 분석 어댑터)를 더한다. 받아쓰기는 기기 음성 인식 라이브러리(`libs/stt`)나 Gemini 받아쓰기 모델 어댑터를 쓴다. 엔진의 경로 고르기와 화면은 바꾸지 않는다.

### 9.2 디자인 시스템

Montage(MIT, v4.0.0 태그 고정)의 토큰과 컴포넌트를 Compose 공통 코드로 옮겨 `ui/design` 에 둔다(ADR 0018).

- 옮기는 것: 색 238개와 다크 색 148개(XML 값을 Kotlin 상수로), Pretendard 글꼴 4종, 아이콘 vector, 컴포넌트
- 안 옮기는 것: 원티드 로고, 워드마크, 로딩 애니메이션
- 고지: MIT 전문과 "Copyright (c) Wanted Lab, Inc.", Pretendard SIL OFL 1.1 을 `THIRD_PARTY_LICENSES.md` 에, "디자인 시스템: Montage by Wantedlab (MIT)" 를 앱 정보 화면과 README 에
- 강조색: 시맨틱 색 가운데 brand 계열만 우리 주홍으로 바꾼다. 라이트 `#C83F1A`(버튼, 글자), 장식 `#E9572B`(그래프, 진행 막대. 글자 배경에는 쓰지 않는다), 다크 `#FF8A62`(위 글자는 검정 계열). 값과 대비는 `product.md` 의 「디자인 시스템」 절에 있다

네이티브로 그리는 곳은 하단 탭(Android Material 3 Expressive NavigationBar 계열, iOS SwiftUI TabView 와 Liquid Glass)과 뒤로가기(Android 예측 뒤로가기, iOS 뒤로 버튼과 가장자리 스와이프)다. 이 두 곳은 사용자가 OS 마다 손에 익은 동작이라 플랫폼 것을 쓴다. 하위 화면의 탭 표시도 플랫폼을 따른다. Android 는 최상위 탭 화면(홈, 기록, 설정)에서만 탭을 보이고 하위 화면에서 숨기고, iOS 는 리포트 상세 같은 하위 화면에도 탭을 남긴다. 시험 진행과 녹음 화면은 두 플랫폼 모두 탭 없는 전체 화면이다. 이 차이는 앱 틀의 화면 경로 표 하나에 두고 화면 모듈은 모른다. 나머지 화면 안 요소는 모두 Montage 로 그린다. 공유 시트와 파일 고르기는 네이티브 후보로만 둔다.

네이티브 부분이 관리하기 어려우면 Montage 로 완전히 통일한다. 미리 확인 노드 `s4` 에서 Montage 화면 위에 네이티브 탭과 뒤로가기를 얹어 보고, `product.md` 「디자인 시스템」 절의 기준 넷 가운데 하나라도 걸리면 통일로 바꾸고 이 절에 적는다.

확인 결과 네이티브를 유지한다. `s4` 에서 기준 넷 모두 해당하지 않았다(`spikes/native-chrome/result.json`). iOS 시험 화면의 탭 숨기기는 보일 때 `.automatic`, 숨길 때 `.hidden` 으로 쓴다.

화면 모드는 설정에서 시스템 따라가기, 라이트, 다크 중에 고르고 기본값은 시스템 따라가기다(F9.1). Montage 의 라이트, 다크 토큰을 이 값으로 고른다.

모든 화면에서 edge-to-edge 를 켠다. 배경과 스크롤 콘텐츠는 시스템 바 아래까지 그리고, 버튼과 글은 시스템 바, 컷아웃, 키보드 인셋 안쪽에 둔다. iOS Compose 화면도 배경은 안전 영역 밖까지, 콘텐츠는 안전 영역 안에 둔다.

- `s1` 의 음성은 macOS 합성 음성이다. 사람 녹음의 발음, 머뭇거림, 잡음에서 멈춤 오차와 단어 오류율은 품질 확인 도구로 다시 잰다. 조각 여러 개에 구조화 출력을 함께 쓰는 요청은 503 과 429 에 막혀 결과를 못 얻었다
- `s3` 은 기기 마이크만으로 한 번 쟀다. 이어폰, 블루투스, 전화나 알람 같은 중단은 일으켜 보지 않았다. Android 화면 꺼짐 녹음은 이 단계에서 재지 않았다
- `s2` 의 사람 청취 판정. 직접 들어 보고 연습이 안 될 만큼 다르면 8절의 대안(Gemini 음성 미리 만들기)으로 바꾼다
