# 화면 품질

화면을 만들거나 고칠 때 이 원칙을 따른다. 제품 요구사항(`docs/specs/product.md`)이나 설계 문서가 다르게 정한 것이 있으면 그쪽을 따른다.

이 앱은 시험 연습 도구다. 사용자는 시간 압박 속에서 녹음 버튼을 누르고 문항을 읽는다. 그래서 화면은 눈에 띄는 장식보다 빨리 읽히고 틀리지 않게 눌리는 쪽을 고른다. 아래 원칙은 그 판단에서 나온다.

디자인 시스템은 Montage 토큰과 컴포넌트(`ui/design`), 서체는 Pretendard, 강조색은 주홍(라이트 `#C83F1A`, 다크 `#FF8A62`)이다. 하단 탭과 뒤로가기만 플랫폼 네이티브로 그린다(ADR 0018). Montage 를 옮기기 전(노드 `c5`)까지는 여기 적힌 플랫폼 기준을 지키고 색은 역할 토큰으로만 쓴다.

## 1. 원칙 18개

1. **터치 영역은 Android 48x48dp, iOS 44x44pt 이상이다.** 아이콘이 24dp 여도 눌리는 영역은 넓힌다. 녹음 중에 손가락이 엇나가 다른 버튼을 누르면 답변을 다시 해야 한다. 붙어 있는 두 터치 대상 사이는 8dp 이상 띄운다.
2. **글자 대비는 본문 4.5:1 이상이다.** 큰 글자(18sp 이상, 굵으면 14sp 이상)와 아이콘, 입력칸 테두리는 3:1 이상이다. 라이트와 다크 둘 다 잰다. 회색 보조 문구가 가장 자주 기준 밑으로 떨어진다.
3. **간격은 4dp 배수, 기본은 8dp 배수다.** 값은 간격 토큰에서만 꺼낸다. 테마 파일 밖에서 `13.dp`, `17.dp` 같은 리터럴을 쓰지 않는다. 묶인 요소 사이는 좁게, 묶음과 묶음 사이는 넓게 둔다. 화면마다 간격이 조금씩 다르면 사용자는 어디까지가 한 묶음인지 읽지 못한다.
4. **글자는 역할로 고른다.** 테마의 타입 스케일(display, headline, title, body, label)에서 고르고 화면마다 `fontSize` 를 손으로 정하지 않는다. 단위는 `sp` 라서 사용자 글자 크기 설정을 따른다. 본문 기준은 Android 16sp, iOS 17pt 이고, 어떤 글자도 11pt 아래로 내리지 않는다.
5. **강조는 크기와 굵기로 한다.** 제목 한 단어만 다른 색이나 기울임으로 바꾸지 않는다. 그라디언트 글자를 쓰지 않는다. 제목 위에 작은 대문자 라벨을 얹지 않는다. 강조가 여러 곳에 있으면 어디가 중요한지 오히려 안 보인다.
6. **색은 역할 토큰에서만 꺼낸다.** `primary`, `onSurface`, `surfaceContainer` 처럼 쓰고 컴포저블 안에 `Color(0xFF...)` 를 쓰지 않는다. 다크 모드, 고대비, 동적 색이 토큰 하나를 바꾸는 것으로 끝나야 하기 때문이다. 강조색은 하나다. 보라나 남색에서 분홍으로 넘어가는 그라디언트를 기본값으로 쓰지 않는다.
7. **높이는 톤 표면으로 나타낸다.** 표면 색 단계(`surfaceContainerLowest` 부터 `surfaceContainerHighest`)로 위아래를 보인다. 그림자는 다이얼로그, 메뉴처럼 실제로 떠 있는 요소에만 준다. 모든 카드 밑에 같은 옅은 그림자를 깔지 않는다. 다크 테마 배경은 순검정 대신 `surface` 를 쓴다.
8. **카드를 기본 그릇으로 쓰지 않는다.** 같은 크기 카드(아이콘, 제목, 설명)를 격자로 늘어놓아 화면을 짜지 않는다. 카드 안에 카드를 넣지 않는다. 묶음은 여백과 구분선으로 먼저 나누고, 눌러서 들어가는 단위일 때만 카드를 쓴다.
9. **모서리 반경은 shape 스케일 안에서만 고른다.** 4, 8, 12, 16, 28dp 다섯 단계다. 안쪽 요소의 반경은 바깥 요소보다 크지 않게 한다(바깥 반경에서 안쪽 여백을 뺀 값).
10. **유리와 흐림은 iOS 시스템 크롬에만 쓴다.** 탭 바, 시트, 알림창처럼 시스템이 직접 그리는 곳이다. 문항 화면, 목록 행, 본문 배경에는 쓰지 않는다. Android 화면에 유리 효과를 흉내 내지 않는다. 반투명 위의 글자는 배경에 따라 대비가 바뀌어 원칙 2를 지킬 수 없다.
11. **플랫폼마다 그 플랫폼의 내비게이션과 컨트롤을 쓴다.** Android 는 하단 내비게이션 바(아이콘과 라벨 둘 다)와 시스템 뒤로가기, 예측 뒤로가기를 살린다. iOS 는 탭 바와 왼쪽 가장자리 스와이프 뒤로가기를 막지 않는다. 한쪽 플랫폼의 스위치, 다이얼로그 모양을 다른 쪽에 옮겨 쓰지 않는다. 사용자는 다른 앱에서 익힌 손동작 그대로 이 앱을 쓴다.
12. **모든 화면은 edge-to-edge 다.** 끄는 화면을 두지 않는다. 콘텐츠는 `WindowInsets`(시스템 바, 디스플레이 컷아웃, 키보드)로 안쪽 여백을 잡고, 배경과 스크롤 콘텐츠는 시스템 바 아래까지 그린다. iOS Compose 화면도 안전 영역 밖까지 배경을 그리고 콘텐츠만 안전 영역 안에 둔다. Android 16 기기에서는 edge-to-edge 를 어차피 끌 수 없다. 기기마다 화면이 달라지지 않게 처음부터 전 화면을 같은 방식으로 맞춘다. 상태 바 높이를 숫자로 박지 않는다. 기기마다 높이가 다르다.
13. **모션은 상태가 바뀌었거나 진행 중임을 알릴 때만 쓴다.** 길이, 곡선, 동작 줄이기는 2절을 따른다. 화면마다 같은 페이드업 등장, 장식용 무한 반복 애니메이션을 넣지 않는다.
14. **모든 상태를 만든다.** 로딩(완성 화면과 같은 모양), 빈 화면(다음에 할 일 하나), 오류(무엇이 잘못됐고 어떻게 회복하는지), 비활성. 말하기 앱이라 마이크 권한 거부와 녹음 실패 화면이 반드시 있어야 한다.
15. **문구는 사용자의 말로 쓴다.** 버튼은 누르면 일어나는 일을 쓴다("제출" 대신 "답변 보내기"). 같은 동작은 흐름 내내 같은 이름으로 부른다. "손쉽게", "완벽한" 같은 홍보 문구와 지어낸 수치를 넣지 않는다. 오류 문구는 사과하지 않고 원인과 해결을 쓴다. 문구가 정해지지 않았으면 지어내지 말고 묻는다.
16. **아이콘은 한 세트, 한 굵기로 쓴다.** 이모지를 아이콘 대신 쓰지 않는다. 이모지는 플랫폼마다 그림이 달라 두 앱의 화면이 서로 다르게 보인다.
17. **누른 뒤 0.3초 넘게 걸릴 수 있는 버튼(네트워크, 파일, 무거운 계산)은 그 버튼에 처리 중 표시를 하고 끝날 때까지 화면의 다른 입력을 막는다.** 버튼 크기는 바뀌지 않는다. `MontageButton(loading = true)` 를 쓴다. 표시가 없으면 사용자는 눌리지 않은 줄 알고 다시 누르거나 다른 곳을 누른다.
18. **에뮬레이터와 시뮬레이터 화면으로 확인한다.** 라이트와 다크, 큰 글자(Android 200%, iOS 가장 큰 접근성 크기)에서 잘리는 글자가 없는지 본다. 코드만 보고 "맞게 그렸다"고 판단하지 않는다.

## 2. 움직임

글을 읽지 않아도 지금 어디쯤인지, 무엇이 바뀌었는지, 결과가 어떤지 보이게 하려고 움직임을 쓴다. 시험 중인 사용자는 문장을 읽을 여유가 없다. 문항 진행, 녹음 중, 저장 완료, 점수가 글자로만 있으면 눈이 화면 위쪽 문장으로 돌아가야 한다.

움직임의 모양은 이 앱이 다루는 것에서 가져온다. 목소리(출렁이는 띠), 소리 물결(모였다 흩어지는 점), 등급 눈금(미끄러져 멈추는 구슬)이다. 흔한 회전 원, 막대 로딩, 화면마다 같은 페이드업은 쓰지 않는다.

- **상태 변화나 진행을 알릴 때만 움직인다.** 문항을 끝내 진행 점이 차오르는 것, 저장이 끝나 체크가 그려지는 것, 점수가 나와 숫자가 굴러 올라가는 것이다. 꾸미려고 도는 반복은 넣지 않는다
- **한 화면에서 주인공 움직임은 하나다.** 두 군데가 크게 움직이면 어디를 봐야 할지 모른다. 녹음 중 화면은 목소리 띠, 리포트는 등급 눈금이 주인공이고, 나머지는 작고 짧게 움직인다
- **길이는 150~400ms 다.** 선택 표시, 버튼 상태 같은 작은 변화는 150ms, 진행 막대와 진행 점, 체크 그리기는 400ms 안에서 끝낸다. 정해진 위치로 가서 멈추는 것(등급 구슬, 숫자 띠)은 스프링으로 1초 안에 멈춘다. 목소리 띠, 기다림 표시처럼 진행이 계속되는 표시만 끝없이 돈다
- **곡선은 둘이다.** 값이 바뀌는 것은 빨리 출발해 천천히 멈추는 곡선(`MontageMotion.spec`), 정해진 위치로 가는 것은 한 번 살짝 지나쳤다 돌아오는 스프링(`MontageMotion.settle`)이다. 여러 번 튕기는 반동은 시험 앱에서 장난스럽게 읽혀 쓰지 않는다
- **값은 `MontageMotion` 에서만 꺼낸다.** 화면에서 `tween(`, `spring(` 을 직접 부르지 않는다. 길이와 동작 줄이기 처리를 한 곳에서 바꾸기 위해서다
- **매 프레임 바뀌는 값은 그리는 단계에서만 읽는다.** 시간, 위치, 크기는 `Canvas` 안이나 `graphicsLayer` 에서 읽고 구성 단계에서 읽지 않는다. 글자를 매 프레임 다시 재지 않는다(숫자는 0~9 띠를 한 번 배치하고 위치만 옮긴다). 부품마다 UI 스레드가 한 프레임에 쓰는 시간의 중앙값을 8ms 아래로 둔다(`MotionDeviceTest`)
- **화면이 안 보이면 멈춘다.** 계속 도는 표시는 `rememberFrameSeconds()` 를 쓴다. 앱이 뒤로 가면 프레임 시계가 서서 그림도 멈추고 배터리를 쓰지 않는다
- **동작 줄이기가 켜지면 움직이지 않고 끝 장면을 바로 보인다.** Android 애니메이션 제거, iOS 동작 줄이기가 켜지면 `MontageMotion` 이 바로 끝 값으로 건너뛴다. 계속 도는 표시는 보기 좋은 한 장면으로 멈춘다. 움직임이 빠져도 같은 정보가 남아야 하니 움직임 하나로만 정보를 전하지 않는다
- **축하는 기다린 결과가 화면을 보는 중에 나왔을 때만 한 번 터진다.** 이미 나온 등급이나 분석을 다시 열면 상태가 바뀐 게 아니라서 터지지 않는다. 예외는 앞 기록과 비교해 처음 보는 변화다(앞 회차보다 오른 등급, 지난번에 본 것보다 오른 약점 점수). 이건 저장소의 본 표시로 한 번만 축하하고, 본 표시는 사용자가 그 축하를 볼 수 있을 때 남긴다. 회차 리포트 맨 위 등급처럼 열자마자 보이는 것은 열 때, 기록 맨 아래 약점 줄처럼 스크롤해야 보이는 것은 그 줄이 그려질 때다. 열 때 남기면 스크롤 아래 축하를 못 보고 지나갈 수 있다. 결과는 늘 체크나 문구가 전하고 축하 조각은 꾸밈이다. 축하는 1.4초까지 써도 되는 유일한 한 번짜리 움직임이다. 동작 줄이기면 조각을 그리지 않고 진동만 낸다
- **목록은 새로 들어온 줄만 나타난다.** 화면을 보는 동안 들어온 줄만 짧게 나타나고 밀린 줄은 미끄러진다(`montageItemMotion`). 탭을 오가거나 다시 열 때 목록 전체가 등장하지 않는다
- **누름과 켜짐은 작게 움직인다.** 버튼과 칩은 누르는 동안 0.96 으로 줄고, 꺼져 있던 버튼이 켜지면 한 번 살짝 튄다. 교정을 틀림으로 표시하면 고친 문장에 주홍 줄이 왼쪽부터 그어진다(`MontageListCell(struck)`)
- **움직임이 끝날 때까지 입력을 막지 않는다.** 처리 중 막기는 1절 17번 원칙대로 일이 끝날 때까지만이다
- **스크린샷은 멈춘 끝 장면이다.** 테스트 시계를 멈추고 넘겨 끝 장면을 찍는다. 동작 줄이기에서 첫 프레임이 끝 장면과 같은지도 같은 테스트에서 본다
  - 예외는 축하 하나다. 축하는 터진 뒤 조각이 다 사라져 끝 장면이 빈 영역이라, 터지는 중 한 장면(시험 끝 0.5초처럼 정한 시각)을 찍는다. 대신 `MotionTest` 가 끝나면 남는 조각이 없는지, 동작 줄이기면 처음부터 아무것도 그리지 않는지 본다

### 기다림

0.3초를 넘을 수 있는 기다림은 세 가지를 모두 보인다. 사용자는 기다리는 동안 앱이 멈췄는지, 기다리면 무엇이 나오는지, 얼마나 더 걸리는지를 묻는다.

1. **기다리는 중이라는 것이 움직임으로 바로 보인다.** 버튼 안이면 처리 중 표시(1절 17번), 화면 한가운데의 기다림이면 `MontageGatheringDots`
2. **기다리면 무엇을 얻는지 문장으로 보인다.** "분석 중" 이 아니라 "답변을 분석하고 있어요. 문법 교정, 한 단계 위 표현, 말 속도가 곧 나와요" 처럼 결과물을 쓴다
3. **얼마나 걸릴지 알 수 있으면 보인다.** 단계가 있으면 진행(답변 7개 중 4개 분석), 보통 걸리는 시간을 알면 그 시간("보통 10초 안팎")을 쓴다. 모르면 지어내지 않는다

공통 부품은 `ui/design` 에 있다. 새로 만들기 전에 이걸 먼저 쓴다.

| 부품 | 모양 | 쓰는 곳 |
|---|---|---|
| `MontageVoiceRibbon` | 주홍 띠 세 겹이 다른 박자로 출렁이고 목소리가 크면 부푼다 | 녹음 중, 장비 점검 |
| `MontageGatheringDots` | 흩어진 점이 왼쪽부터 모여 소리 물결이 됐다 흩어진다 | 질문 불러오기, 답변 분석 같은 기다림 |
| `MontageGradeScale` | 빛나는 구슬이 눈금 위로 미끄러져 등급 범위 가운데에 멈추고 불꽃이 튄다 | 회차 리포트 등급, 기록의 회차 등급 |
| `MontageStepTrail` | 문항마다 점, 끝내면 선이 다음 점까지 뻗고 점이 톡 차오른다 | 문항 진행, 서베이 Part 진행 |
| `MontageCheckMark` | 옅은 원 안에 체크가 그려지고 물결이 한 번 퍼진다 | 키 확인 성공, 저장 완료, 복사 완료 |
| `MontageCountUp` | 숫자 하나하나가 0 에서 굴러 올라가 멈춘다 | 점수, 유형별 점수 |
| `MontageProgressBar` | 값이 바뀌면 새 값까지 차오르는 얇은 막대 | 약점 유형 점수 막대 |
| `MontageCelebration` | 큰 축하는 짧은 막대와 점 조각이 터졌다 떨어지고(1.4초, 축하 진동), 작은 축하는 불꽃이 둥글게 한 번 퍼진다(0.7초, 성공 진동) | 큰 축하: 15문항을 다 마쳤을 때, 보는 중에 회차 등급이 나왔을 때, 바로 앞 회차보다 오른 등급을 처음 볼 때. 작은 축하: 키 저장, 앱에서 처음 끝난 답변 분석을 보는 중일 때, 지난번에 본 것보다 오른 약점 점수를 처음 볼 때. "처음"은 저장소의 본 표시로 정해서 앱을 다시 켜도 다시 터지지 않는다 |

공통 코드에서 그리는 화면은 두 파일을 모두 지킨다. 두 플랫폼 수치가 다르면 큰 쪽을 쓴다(터치 영역은 48dp).

## 4. 확인 순서

화면 PR 을 올리기 전에 다음을 본다.

1. 코드 검색. 테마 파일 밖에 `Color(0x`, `fontSize = ` 리터럴, `tween(` 과 `spring(` 직접 호출, 숫자 `.dp` 간격이 없는지
2. Android 스크린샷(Roborazzi). 라이트, 다크, 글자 200%, 360dp 폭. 상태마다 한 장(`testing` 스킬 5절)
3. Android 접근성 자동 검사. 라벨 누락, 대비, 작은 터치 영역, 읽는 순서
4. iOS 시뮬레이터. 라이트, 다크, 가장 큰 접근성 글자, 동작 줄이기, 투명도 줄이기. 설정 경로는 `references/ios.md` 머리에 있다
5. TalkBack, VoiceOver 로 화면 한 바퀴
